## 슬라이드 2 — 문제 정의

센서마다 설정하는 방법이 다르다. 벤더 웹 UI, SDK, CLI, ROS 파라미터가 섞여 있고,
무엇을 언제 누가 바꿨는지 남지 않는다. 차량에 센서가 늘어날수록 이 비용이 선형으로
늘고, 잘못 바꿨을 때 되돌릴 방법이 없다.

**설계 원칙 두 개**

1. **YAML 이 주인이다.** 모든 변경은 parameter file 에 먼저 저장되고, 노드의
   런타임 상태는 그 결과일 뿐이다.
2. **장치에는 드라이버만 쓴다.** Config App 은 센서 API 를 직접 부르지 않는다.
   YAML 을 쓰고 드라이버 노드에 적용을 요청한다.

**말할 것**: 2번이 중요하다. 도구가 센서 API 를 직접 부르면 드라이버가 모르는
상태가 생겨서, 드라이버 재시작 한 번에 설정이 날아간다.

## 슬라이드 3 — 적용 트랜잭션 (핵심 설계)

```
검증 → 계획 → YAML 기록(원자적 쓰기) → git commit
                                          ↓
                                  unit 재시작
                                          ↓
                      계층별 되읽기 + 데이터 흐름 확인
                                          ↓
                      통과 → 완료   /   실패 → 자동 롤백(git revert)
```

- **계층(layer)** 개념: `device`(센서 펌웨어에 기록) / `driver`(노드 내부) /
  `global`(전역 frame 등). 계층마다 되읽기 방법이 다르다.
- `device` 계층은 **장치에서 되읽어** 확인한다. 노드가 "받았다"고 답하는 것으로는
  부족하다 — 센서가 값을 거부하거나 보정할 수 있다.
- 롤백은 항상 **새 commit(revert)** 으로 쌓는다. `reset --hard` 로 덮으면 실패한
  시도가 이력에서 사라져 감사 로그 요건과 모순된다.

**말할 것**: 되읽기를 장치까지 내려가서 하는 것이 이 도구의 차별점이다. 실제로
이번에 그게 없으면 못 잡는 문제를 발견했다(슬라이드 7).

## 슬라이드 4 — 이번 구간 성과: 실센서 연동

실제 적용을 수행하고 전 단계가 동작하는 것을 확인했다.

```
status  : succeeded
commit  : b03e0b03
message : 적용과 반영 확인을 모두 통과했다.
  lidar_mode      요청 512x10 → 장치 실제값 512x10   (출처: /ouster/get_config)
  /ouster/points  기대 10.0 Hz → 실측 7.5 Hz         (통과)
```

되돌리기도 확인했다. 이력에서 commit 을 골라 복원(파일) → 다시 적용(장치) 두
단계로 `512x10` → `1024x10` 원복.

| 측정 항목 | 값 |
|---|---|
| `/ouster/points` | 9.99 Hz (`services.yaml` 의 기대값 10.0 Hz) |
| `/ouster/imu` | 99.95 Hz |
| 수집 파라미터 | 41개, drift 0 |
| 스키마 매칭 | `mapped` (설명·허용값·계층·등급 부착) |
| 적용 1회 소요 | 25~30초 (센서 초기화 20초 포함) |
| 누적 설정 이력 | git commit 15개 |

## 슬라이드 5 — 쟁점 ①: 펌웨어와 SDK 의 호환 경계

**증상**: 최신 드라이버가 센서에 아예 연결되지 않았다.

```
Error connecting to sensor 10.5.5.87:
  CurlClient::execute_request failed for url:
  [10.5.5.87/api/v1/sensor/metadata/sensor_info] code: [404]
```

**원인**: Ouster 가 펌웨어 2.2 에서 센서 HTTP API 를 재편했다. 이 센서는 구형
엔드포인트만 갖고 있고, SDK 0.16.0 이 구형 구현을 삭제했다.

| 경로 | FW v2.1.2 |
|---|---|
| `/api/v1/sensor/cmd/get_sensor_info` (구) | 200 |
| `/api/v1/sensor/metadata/sensor_info` (신) | **404** |

메타데이터에는 **beam 각도 128개와 데이터 포맷**이 들어 있다. 이걸 못 읽으면 UDP
패킷을 포인트로 해석할 수 없다. 그래서 "일부 기능 없음" 이 아니라 **연결 자체가
불가** 로 나타난다.

**해결**: 구형 구현이 살아 있는 마지막 릴리스를 소스 특정해 고정했다.

```cpp
// ouster-ros jazzy-0.13.15 가 포함한 SDK
if (fw.major == 2) {
    switch (fw.minor) {
        case 1: return std::make_unique<SensorHttpImp_2_1>(hostname, timeout_sec);
```

| ouster-ros | 릴리스 | FW 2.1 |
|---|---|---|
| `jazzy-0.13.15` | 2025-10-24 | **지원** ← 고정 |
| `jazzy-0.14.x` 이후 | 2026-03~ | 없음 |

**대가**: 관리 가능한 device 계층 파라미터가 27개 → **7개** 로 줄었다. 구버전
드라이버가 나머지를 ROS 파라미터로 노출하지 않는다. 센서 HTTP API 로는 설정할 수
있지만 도구의 관리 범위에서 빠진다.

**말할 것**: 펌웨어를 올리면 이 제약이 사라진다. 올릴지 여부가 의사결정 사항이다
(슬라이드 9).

## 슬라이드 6 — 쟁점 ②: 적용 트랜잭션의 검증 타이밍

**증상**: **정상 적용이 롤백됐다.** 값은 제대로 반영됐는데 도구가 실패로 판정했다.

```
status : rollback_failed
  lidar_mode → "/ouster/get_config 를 그래프에서 찾을 수 없다"
  /ouster/points → "발행자가 없을 수 있다"
```

**원인 두 겹**

1. 재시작 후 **노드 이름만** 기다렸다. 이 드라이버는 노드를 먼저 만들고 센서에
   접속한 뒤(20초 이상) 서비스와 토픽을 띄운다. 되읽기가 그 사이에 돌았다.
2. 1번을 "필요한 서비스가 보일 때까지" 로 고쳤는데도 재발했다. **재시작 직후의
   그래프 정보를 신뢰할 수 없다** — 사라진 노드의 서비스가 DDS discovery 에
   한동안 남아 "준비됐다" 고 오판한다.

**해결**: 믿을 수 있는 신호는 **실제 호출이 성공하는 것** 하나뿐이다. 반영 확인을
단발 표본에서 **수렴 대기** 로 바꿨다. 일시적 실패(응답 없음, 표본 0건)는 최대
60초 재시도하고, 값이 돌아왔는데 다르면 재시도하지 않는다(그건 최종 답이다).

함께 고친 것: 센서가 끊겼다 돌아와도 유닛이 복구되지 않는 문제. 종료 경로가
정상 종료(exit 0)라 `Restart=on-failure` 가 걸리지 않았다 → `Restart=always`.

회귀 방지 테스트 4개를 추가했다 (재시도 동작 2개, 준비 완료 대기 2개).

**말할 것**: 분산 시스템에서 "상태 조회" 와 "실제 가용성" 이 다르다는 전형적인
사례다. 그래프는 캐시이고, 유일한 진실은 호출해보는 것이다.

## 슬라이드 7 — 쟁점 ③: 관측 가능성의 한계 (거짓 "일치")

**증상**: drift 0 인데 실제로는 어긋나 있었다.

| | 값 |
|---|---|
| parameter file (저장값) | `udp_profile_lidar: RNG19_RFL8_SIG16_NIR16` |
| 노드의 런타임 파라미터 | `RNG19_RFL8_SIG16_NIR16` |
| **센서의 실제 동작** | **LEGACY** |

드라이버가 조용히 떨어뜨린다: `No lidar profile found. Using LEGACY lidar profile`

목록 화면의 drift 는 *저장값 ↔ 노드 파라미터* 비교다. **장치까지 비교하지 않는다.**
장치 되읽기는 적용 트랜잭션 안에서만 돈다. 그래서 "노드는 받았다고 하는데 장치는
다른" 상태가 일치로 보인다.

**조치**
1. 저장값을 장치 실제값 `LEGACY` 로 정정했다.
2. 이 파라미터를 `device` 계층에서 제외했다 — FW 2.1 의 `get_config` 응답에 그
   키가 없어 되읽을 대상이 없다. 드라이버가 "요청하는" 값일 뿐 장치에 기록되지
   않으므로 `driver` 계층이 맞다.

**말할 것**: 이것이 슬라이드 3 의 "장치까지 되읽는다" 가 왜 필요한지 보여주는
실례다. 동시에 **상시 drift 탐지에는 아직 장치 비교가 없다**는 한계도 드러낸다 —
개선 과제다.

## 슬라이드 8 — 검증 상태

### 실측으로 확인된 것

| 항목 | 방법 |
|---|---|
| 드라이버 ↔ 실센서 연결 (FW v2.1.2) | 컨테이너에서 기동, `configured successfully` |
| 포인트클라우드·IMU 발행 | `/ouster/points` 9.99 Hz, `/ouster/imu` 99.95 Hz |
| 파라미터 자동 수집 | 41개, 스키마 매칭 `mapped` |
| 저장값 머지 순서 (전역이 노드별을 덮음) | `sensor_frame` = global.yaml 값 |
| drift 탐지 | 포트 2건, 프로파일 1건을 실제로 잡음 |
| 허용값 검증 | enum 밖 값 `not_in_enum` 거부 |
| **적용 전 과정** | 저장·commit·재시작·장치 되읽기 통과 (`succeeded`) |
| **자동 롤백** | 되읽기 실패 시 git revert + 재시작, 파일 원복 확인 |
| 이력 복원 | `restore` 로 파일 복원 → 재적용으로 장치 반영 |
| 원본에 없던 파라미터의 롤백 | "되돌린 파일에 없다. 재적용에서 건너뛴다" 로 처리 |
| 유닛 자동 복구 | 정상 종료에서도 systemd 가 재기동 (`NRestarts` 증가 확인) |
| 단위·컴포넌트 테스트 | 256개 통과 |

### 아직 확인되지 않은 것

- 차량 상태 연동 (안전 게이트는 `mode: open` — 개발·벤치 전용)
- 인증·권한 (역할을 HTTP 헤더로 받고 있고, 없으면 engineer 로 간주)
- 점검 규칙 R1·R3~R9 (R2·R4 만 동작)
- 다중 센서·다중 unit 환경 (현재 등록된 서브시스템은 lidar_top 하나)
- 장시간 안정성 (연속 가동 시험 없음)

## 슬라이드 9 — 알려진 제약과 다음 단계

### 제약 (발표에서 솔직히 밝힐 것)

| 제약 | 내용 |
|---|---|
| **인증이 없다** | 역할·사용자를 HTTP 헤더로 받는다. 외부 노출 금지. UI 가 사용자 헤더를 보내지 않아 **감사 로그에 `anonymous` 로 기록된다** — 명세의 감사 요건을 아직 만족하지 못한다 |
| **안전 게이트가 차량 상태를 모른다** | 주행 중 변경 차단이 미구현. 차량 탑재 전 필수 |
| **device 계층 7개뿐** | 드라이버 버전 고정의 대가 (슬라이드 5) |
| **상시 drift 가 장치를 보지 않는다** | 슬라이드 7 |
| **개발 호스트가 특수하다** | 호스트가 Ubuntu 26.04 라 ROS 2 를 컨테이너에서 돌린다. 실차 IPC/Jetson 은 24.04 네이티브이므로 이 우회가 필요 없다 |

### 의사결정이 필요한 것

1. **센서 펌웨어를 올릴 것인가.** 올리면 device 계층이 7개 → 27개로 늘고 최신
   드라이버를 쓸 수 있다. 다만 2021년 펌웨어에서 올리는 작업이고 공장 캘리브레이션
   백업이 선행돼야 한다(기준 스냅샷은 확보해 둠).
2. **M3 를 다음 단계로 둘 것인가.** 인증·역할·감사 로그. 차량 탑재의 전제 조건이다.

### 제안하는 다음 단계

1. UI 가 사용자 헤더를 보내게 수정 (감사 로그 정상화) — 작은 변경, 즉시 가능
2. 상시 drift 에 장치 비교 추가
3. M3 (인증·역할·감사 로그)
4. 두 번째 센서 온보딩으로 다중 unit 경로 검증
